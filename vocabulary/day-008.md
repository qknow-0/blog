# Day 008 — 2026-06-21

## 1. Throughput /ˈθruːpʊt/（吞吐量）

系统单位时间内处理的数据量或请求数。衡量性能的经典指标——throughput 高意味着能扛更多流量。通常和 latency 一起讨论：batch 处理提高 throughput 但可能增加 latency。

## 2. Latency /ˈleɪtənsi/（延迟）

一个请求从发出到收到响应之间的时间。低延迟不等于高吞吐——一个系统可以吞吐很高但每个请求都很慢（大量并发），也可以延迟很低但吞吐上不去（串行处理）。

## 3. Polling /ˈpoʊlɪŋ/（轮询）

定时重复检查某个状态是否变化。短轮询（short polling）：隔几秒问一次「好了没？」；长轮询（long polling）：问了之后挂着，等服务端有数据再响应。WebSocket 出现后长轮询用得少了。

## 4. Backpressure /ˈbækˌpreʃər/（背压）

当下游处理不过来时，通知上游减速的机制。Reactive Streams 规范（Java/RxJS/Project Reactor）把它标准化了：下游通过 `request(n)` 告诉上游自己能消化多少，防止内存被打爆。

## 5. Deadlock /ˈdedlɒk/（死锁）

两个或多个线程互相等待对方释放资源，每个人都拿着对方要的锁，结果谁都动不了。四个必要条件（互斥、持有等待、不剥夺、环路等待），破坏任意一个就能预防死锁。

## 6. Starvation /stɑːrˈveɪʃn/（饥饿）

低优先级的线程永远得不到 CPU 时间，因为高优先级的线程一直在执行。和死锁不同——死锁是所有人都卡住，饥饿是被卡住的只有一部分人。公平锁（fair lock）可以缓解。

## 7. Race Condition /reɪs kənˈdɪʃn/（竞态条件）

多个线程同时访问共享数据，执行顺序不同导致结果不确定。经典的例子是 `counter++`——这个操作看似一行，实际是读-改-写三步，两步之间可能被另一个线程插入导致计数丢失。

## 8. Lock Contention /lɒk kənˈtenʃn/（锁竞争）

多个线程争抢同一把锁，导致系统吞吐急降。减少锁竞争的方法：减小锁粒度（用读写锁替代互斥锁）、缩短临界区、用无锁数据结构（lock-free）。

## 9. Thread Pool /θred puːl/（线程池）

预先创建一组线程，任务来时分发，用完归还。避免频繁创建销毁线程的开销。几乎所有异步运行时底层都是线程池——tokio、asyncio、Node.js 的 libuv 都一样。

## 10. Load Shedding /loʊd ˈʃedɪŋ/（减载）

当系统负载超过容量时，主动丢弃一部分请求以保护核心功能的可用性。不是 bug，是特性——宁可 10% 的请求失败，也比 100% 的请求都超时强。和 backpressure 是两种应对过载的策略：前者「少接点」，后者「让上游慢点」。

**今日主题：并发、背压、过载保护**

throughput ↔ latency 是性能的一体两面，deadlock ↔ starvation ↔ race condition 是并发的经典三坑，backpressure ↔ load shedding 是过载保护的两种策略。
