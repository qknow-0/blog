# Unsafe Rust：厨房的刀，不是玩具

> 想象你在开车。Rust 的 borrow checker 就是自动驾驶——帮你保持车道、保持车距、不撞墙。但有时候自动驾驶不理解你的意图：你需要一个急转弯、或者倒进一个窄车位。这时候你按了一个按钮，方向盘交给你——这就是 `unsafe`。你还是得遵守交通规则，但现在出事了是你负责。

本文基于 Rust 1.96。

## 自动驾驶和手动模式

Rust 编译器的安全保证就像一个非常谨慎的自动驾驶系统：

```text
自动驾驶模式（safe Rust）：
  你能做什么 → 全自动车道保持、自动刹车、自动泊车
  你不能做什么 → 不会让你撞墙、不会让你闯红灯

手动模式（unsafe Rust）：
  你能做什么 → 方向盘在你手里，想去哪去哪
  你不能做什么 → 油门刹车还是能用，只是方向盘归你了
  你要负责什么 → 撞了墙是你的责任，不是自动驾驶的锅
```

**关键误解**：很多人以为 unsafe 关闭了所有安全检查。完全不是——unsafe 只把五个特定操作的控制权交给你。其他的安全检查仍然在：类型检查还在、借用检查还在、所有权规则还在。

就像手动模式下油门、刹车、转向灯都还在工作——只是方向盘上的自动驾驶锁被解开了。

## 五件自动驾驶不会替你做的事

```text
safe Rust 的世界里，这五件事编译器不让你做：

1. 跟着一张手绘的纸质地图开车（解引用裸指针）
2. 进入一个挂着"危险⚠️"牌子的区域（调用 unsafe 函数）
3. 在一个大家都能随便改的公告栏上写字（访问可变 static）
4. 签一份"我用人格担保"的安全承诺书（实现 unsafe trait）
5. 用一个需要手动切换模式的二合一工具（访问 union 字段）
```

一个一个说。

## 1. 纸质地图：裸指针

标准的 Rust 引用 `&T` 就像手机 GPS 导航——它知道你当前在哪、目的地是哪、路上有没有封路。你跟着走就行，不会出错。

裸指针 `*const T` 就像一张手绘纸质地图——上面画了坐标，但地图对不对、路通不通、有没有断头路，GPS 不管。你拿着地图开车，到了悬崖边是你自己没看清。

```rust
// GPS 导航：绝对不会导到悬崖
let answer = 42;
let gps: &i32 = &answer;    // "前方 200 米右转，目的地到达"
println!("{}", *gps);       // 42，安全到达

// 纸质地图：坐标画了，但路对不对你自己看
let gps_pointer: *const i32 = &answer as *const i32;
// println!("{}", *gps_pointer);  // 编译错误："你拿着手绘地图，我不能让你开"
unsafe {
    println!("{}", *gps_pointer);  // "行，你确定路是对的，那你开"
}
```

纸质地图什么时候有用？当你需要去的地方 GPS 地图上没有——比如调用 C 语言的代码。C 语言活在 Rust 的安全边界之外，它只给你一个内存地址（纸质坐标），没有导航信息。

## 2. 危险区域：unsafe 函数

有些函数门口挂着「⚠️ 危险」的牌子。不是你不能进去——是你进去之前必须确认你知道里面有什么。

```rust
// 普通函数：门口没有牌子，进去不需要想
let x = 42;
let y = x;

// unsafe 函数：门口挂着"⚠️ 进入前确认防护装备"
// std::ptr::read 的作用：从任意内存地址读一个值出来
// 危险在哪：如果那个地址是无效的，程序直接炸
let ptr: *const i32 = &42;
let val = unsafe { std::ptr::read(ptr) };  // "我看到牌子了，防护装备已确认，我要进了"
```

类比：普通函数就像进超市——推门就进。unsafe 函数就像进化工厂——门口有警告标志，进去前你得签安全确认书。unsafe 块就是你的签名：「我了解里面的风险，我会遵守安全规程」。

注意 `unsafe` 是**传染的**——如果你调了 unsafe 函数，你的函数也要么是 unsafe 的，要么你用 unsafe 块包住它。就像化工车间里的安全规定——谁进入谁负责。

## 3. 公共公告栏：可变 static

```rust
// safe 版本：公告栏是锁着的，只能看不能写
static APP_NAME: &str = "my-app";  // 所有人只能看

// unsafe 版本：公告栏没锁，谁都能往上贴纸
static mut COUNTER: u32 = 0;  // 任何人都能改
fn increment() {
    unsafe { COUNTER += 1; }  // 你在公告栏上贴了一张纸
}
```

问题不在「有人写了公告栏」——在**两个人在同一个瞬间写公告栏**。一个人写「销售额 +100」，另一个人写「销售额 +200」，最后公告栏上只剩一个数字。

Rust 说：「公告栏默认上锁。如果你非要开锁，你得进 unsafe 块写——而且出了并发问题你自己负责。」

现实中几乎不需要用 `static mut`。更好的做法是装一个带排队机制的公告栏：

```rust
use std::sync::OnceLock;
use std::sync::Mutex;

fn global_counter() -> &'static Mutex<u32> {
    static COUNTER: OnceLock<Mutex<u32>> = OnceLock::new();
    COUNTER.get_or_init(|| Mutex::new(0))  // 上锁的公告栏
}
```

## 4. 人格担保书：unsafe trait

编译器会自动判断一个类型能不能安全地跨线程传递。规则很简单：如果类型的所有字段都是 `Send` 的，那它自己也是 `Send` 的。

但你包装了一个 C 库的结构体，里面是裸指针。编译器不认识 C 的结构体，它说：「有裸指针？自动判定失败——我不确定它能不能跨线程。」

这时候你写了一份保证书：

```rust
struct CContext {
    ptr: *mut std::ffi::c_void,  // "C 库给的东西，我看不懂"
}

// 编译器："它能不能跨线程用？我判断不了。"
// 你："我知道这个 C 库内部是线程安全的，我担保。"
unsafe impl Send for CContext {}
```

类比：机场安检的行李扫描仪（编译器）看到你箱子里有个不认识的东西。你说「这是专业设备，安全的」，然后签了保证书。如果这东西其实是危险的——你签的字，你负责。

`Send` 和 `Sync` 是 Rust 里最常见的两种 unsafe trait 实现。不是因为它们特别危险——是因为**编译器在 99% 的情况下能自动判断**，只有你用了裸指针这种编译器不认识的东西时，才需要你手动担保。

## 5. 二合一工具：union

你有一把螺丝刀，一头是十字、一头是一字。你转一下就能切换——但你必须记住「当前是哪头」。用错了可能拧花螺丝。

```rust
union FloatOrInt {
    f: f32,   // 当作浮点数用
    i: u32,   // 当作整数用（读出浮点数的二进制表示）
}

let u = FloatOrInt { f: 3.14 };
// println!("{}", u.i);   // 编译错误："你确定现在是整数这头吗？"
let bits = unsafe { u.i };  // "我确定——我要的就是 f32 的二进制表示"
```

这个用得极少。主要在跟 C 打交道或者研究二进制格式时遇到。简单说，如果你不知道为什么需要 union，你就不需要。

## 核心原则：厨房的刀

理解 unsafe 最重要的是这个比喻：

```text
餐厅后厨：
  刀非常锋利 → 切菜时手一滑就见血
  但吃饭的客人碰不到刀
  刀只在后厨（unsafe 模块内部）使用

safe API = 端上桌的菜（安全）
unsafe = 后厨的刀（只在内部用）
```

标准库里的 `Vec<T>` 就是用裸指针管理内存的——但你对 Vec 的操作全是 safe 的：`push`、`pop`、`get`，没有 unsafe 块。

```rust
// Vec 内部类似这样（简化版）
// 后厨——只有厨师看得到刀
struct Vec<T> {
    ptr: *mut T,    // 裸指针——锋利的刀
    len: usize,
    cap: usize,
}

impl<T> Vec<T> {
    // 前厅——客人用 safe API
    pub fn push(&mut self, value: T) {
        // 厨师在 safe 方法内部切菜
        unsafe { self.ptr.add(self.len).write(value); }
        self.len += 1;
    }
}
```

这叫做 **unsafe 是实现细节，不是接口**。你的整个程序里，unsafe 块应该被封装在几个模块里，对外暴露的全是 safe API。

## 什么时候点火、什么时候不点

| 该用 unsafe 了 | 类比 |
|---|---|
| 调用 C 库（FFI） | GPS 导航到边界了，需要看纸质地图进入无服务区 |
| 手写高性能数据结构 | 量产工具不够快，你自己打了一把专用刀 |
| 直接跟操作系统交互 | 你需要在发动机舱里接线，而不是通过方向盘控制 |
| 嵌入式裸机编程 | 没有自动驾驶，你从一开始就在手动模式 |

| 不该用 unsafe | 为什么 |
|---|---|
| borrow checker 太烦了 | 重构代码。绕过检查器就像因为红绿灯太多而闯红灯 |
| 「我想快一点」 | 先测瓶颈在哪。99% 的慢不是因为 safe Rust 的检查 |
| 「不想写 Clone」 | 想清楚是不是真需要避免一次克隆。为了省一次 Clone 引入安全漏洞不值得 |

## 小结

背下这个就行：

```text
unsafe 不是关掉安全气囊——是握住方向盘。
安全气囊还在，安全带还在，刹车还在。
只是方向盘的自动驾驶解锁了。

你握着方向盘，
油门和刹车（类型检查、借用检查）还在工作，
导航（生命周期）也在给你提示。
但方向盘在你手里——撞了就是你打的。
```

五个超能力记不住没关系——用到哪个查哪个。记住一个原则就够了：**unsafe 只在后厨用，端上桌的菜必须是 safe 的**。
