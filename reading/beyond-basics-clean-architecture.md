# 读「不要只满足于软件开发的基础」有感

> 原文核心观点：从结构化编程到领域驱动设计，不是技术的堆叠，而是对依赖关系的深刻理解。不要在基础层面打转，往上走一层，看到的是完全不同的世界。

## 从「能跑就行」到「能改才行」

刚入行的时候，很多人对"好代码"的理解就是——能编译、能运行、功能对。这种阶段会持续很长一段时间，因为日常工作中大多数时候确实是在堆功能。

但总有一天你会碰到一堵墙。这堵墙可能是：

- 改一个"简单"需求需要动十几处代码
- 加一个新功能发现三年前的逻辑已经没人看得懂
- 系统跑了两年的稳定版突然因为一个边界条件崩了

这时候你才意识到：**代码能跑只是及格线，代码能改才是真正的水准**。

而 Clean Architecture（整洁架构）和 DDD（领域驱动设计）这些东西，本质上不是在教你"怎么写代码"，而是在教你"怎么组织代码之间的关系"。

## 依赖方向这个事，真的想明白了吗

文章里那个同心圆图看着简单——外圈依赖内圈，内圈不依赖外圈。但实际工程里把它贯彻到位极难。

举个例子：你的业务逻辑代码里有没有 `import` 某个框架的注解？有没有直接调数据库的 query builder？有没有直接读 HTTP request 对象？

大部分人第一反应是："这不是很正常吗？"

Clean Architecture 说：错了。你的核心业务不应该知道数据库长什么样，不应该知道 HTTP 协议是什么，不应该知道用的是 Spring 还是 Express。这些全是"细节"，而细节应该依赖抽象，而不是反过来。

```
框架、数据库、UI  →  依赖  →  核心业务逻辑
         （外圈）                    （内圈）
```

搞反了这个方向，就等于把你的核心资产绑死在了随时可能换掉的实现细节上。

## 为什么认同

几点深有体会：

### 1. 框架不是你的应用

曾经在一个项目里见过，整个业务逻辑散落在 Controller 和 Service 层，每个方法都带着框架特有的注解和上下文对象。后来要从单体拆微服务，光是把业务逻辑"抠出来"就花了两周——因为它根本分不清哪些是业务、哪些是框架胶水代码。

Clean Architecture 的解法是对的：**把业务逻辑写成纯函数/纯对象，完全不依赖框架，框架只是它的一个可替换外壳**。

### 2. 分层不是目的，解耦才是

很多项目都有 Controller → Service → Repository 的分层，表面上看起来挺有架构感的。但仔细一看，Service 层直接用了 ORM 的实体类，Repository 层把 SQL 异常往上抛，Controller 层直接返回数据库模型给前端。

这不叫分层，这叫**物理切割**。真正的分层是每层只知道自己该知道的事，层与层之间通过接口和 DTO 交流。

### 3. 架构是为变化服务的

最难说服别人的一点是："我又不确定将来会怎么变，为什么要为不确定的变化多写代码？"

问题是，**软件唯一确定的事就是它一定会变**。你现在不拆，两行代码就能完成的事确实更快。但两年后五十个需求叠上去，没有边界的代码就会变成没人敢动的地雷区。

投入结构的代价不是"过度设计"，而是**对变化概率的合理对冲**。

## 自我审视

读完这篇文章，我问了自己几个问题：

- 我现在写的代码，如果下个月要换数据库，改多少行？
- 如果前端从 Web 变成 CLI，业务逻辑能复用多少？
- 一个新人只看我的代码，能不能画出依赖流向？

诚实地说，大多数时候答案并不好看。但至少现在知道该往哪个方向改了。

## 结语

软件开发的基础是能写功能。往上走一步，是能写干净的功能。再往上走一步，是能写经得起时间考验的功能。

Clean Architecture 不是银弹，但它的核心原则——**依赖倒置、关注点分离、内圈不依赖外圈**——值得在每一个项目、每一次 code review 中被反复提醒。
