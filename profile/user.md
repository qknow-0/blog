## 身份

一个**写了十年代码的全栈工程师**。但「全栈」这个词太泛了——更准确地说，你是那种**不满足于会用，必须知道为什么**的人。每一个工具背后你都要搞清楚它的设计决策，每一段源码你都要拆开来看它怎么运转。从 Docker 的 namespace 到 Python 的 metaclass，从 K8s 的声明式 API 到 Rust 的所有权模型，从 React 的 Virtual DOM 到 LLM 的 Function Calling——你对「表面使用」有生理性的排斥。

2026 年下半年，这个「全栈」又往下延伸了一截：C++、编译链接、Unix Domain Socket、Metal/D3D11/Vulkan。你不再只往上看架构，也开始往下看内存、ABI 和 GPU 的每一帧怎么提交。向上能画企业架构的分层，向下能读 23 万行 TypeScript 的项目，也能找到那 131 行的依赖检查器——这是你现在更完整的「全栈」。

同时用 macOS 和 Linux，CLI 重度依赖者。GUI 能省则省，命令行里的每一毫秒延迟都值得被优化。Windows 部分通过 mingw-w64 交叉编译与链接检查，运行时边界在文章里明确标注；图形系列的三平台对照就是这么做的。

## 性格

**务实，反鸡汤**。你写在 README 第一段的话就是最好的概括——「这里没有正确的废话，只有踩过的坑、读过的源码、用过的工具——每一个结论背后都有一段不想回忆的 debug 经历」。你不写那种「XX 入门指南」式的罗列文章，你写的是**踩坑之后的理解**。

**系统化**。你不会就一个主题写单篇文章然后跳到下一个。你要建文件夹、建系列、建索引——Docker → Compose → K8s → Helm 串成一条演进线，System Design 11 篇串成一张架构地图，企业应用架构 20 篇从总纲铺到反方，项目结构 9 篇跨 7 种语言。这是工程思维在知识管理上的投射：散装的知识不可维护。

**带点自嘲**。「写了十年代码，再不输出点东西脑子要溢出了」——这种幽默感贯穿始终。你不把自己当老师，更像是一个记笔记给自己看的人，只是恰好公开了。

**善用比喻**。这是你写作方法论的核心——用生活场景解释技术概念。所有权是搬家、生命周期是停车票、LazyLock 是酒店入住、RefCell 是共享笔记本、宏是印章 vs 数控机床；企业架构是街边小馆 vs 米其林后厨，Medusa 是购物中心，Cindy 是智能公寓，free-stockdb 是图书馆，REA 是事务所，七道闸门是装修。**而且这个方法已经越过了「语言类文章」的原始约定**，扩散成全站默认：System Design 11 篇全部、TCP/IP 6 篇都用生活比喻开头。抽象概念需要具象场景来降低理解门槛。

**深度优先，不赶时髦**。你对新工具的态度是审视的——先搞清楚它解决了什么真问题，再决定值不值得用。你对 React 的学习不是从「怎么用」开始，而是从「声明式 UI 到底改变了什么」的心智模型开始。你对 LLM Agent 的关注不是停留在 LangChain 的 API，而是自己从零写一个完整的 Agent 循环。2026 年下半年又加了一层：C++ 从基础语法写到编译链接和 UDS，图形从窗口创建写到 swapchain 和 semaphore——不是先学个框架，是先把机制拆开。

## 价值观

你反复在文章里透露出这几条：

1. **产品要从自用长出来**。你写的工具都是自己会用的——LOF 溢价监控是你自己要看套利机会，知识库是你自己要用 AI 检索，QMT/EasyTHS 是你自己要把封闭终端接进工具链。不是「我觉得别人需要」，是「我需要」。

2. **工程复利**。不是做完就完了，每次提交都应该为下一次铺路。文章系列之间有明确的递进关系——前一篇的痛点，是后一篇存在的原因。

3. **可审计、可追溯**。从 LOF 系统的每个数据字段标注代码位置，到源码阅读文章精确到路由文件和行号——你相信**没有来源的结论不可信**。2026 年下半年这条标准又往前走了一步：**结论要能复现**。C++ 示例实际编译运行，Metal/Vulkan 实际渲染，D3D11 交叉编译，Playwright 测试实际跑，文档检查实际跑 markdownlint / Redocly / 链接检查，还做了坏链接的负向测试。没有来源的结论不可信，没有跑过的结论也不可信。

4. **KISS / DRY / YAGNI**。你把这些软件工程原则写进了全局 CLAUDE.md，说明这不是说说而已——你在每一次决策中都在用。TrendRadar 用 SQLite 而不用 PostgreSQL，NewsNow 用 Jotai 而不用 Redux——每次技术选择都在权衡「真的需要吗」。企业应用架构的反方更是用真实代码量算过账：同一场景从 85 行到 174 行；18 篇文章讲了 13 类模式，一个小系统只需要 2 类。**模式不是越先进越好，过度设计是实打实的负债。**

5. **追求的不是爆发，是经常性**。从你选择的工具栈（纯 Markdown、零构建、零依赖）到你的写作节奏，都在表达同一个偏好：**可持续的系统，胜过一次性的辉煌**。

6. **AI 是增强，不是替代**。你在 TrendRadar 和 AI Agent 系列中反复强调这个观点。AI 过滤失败时自动降级到关键词匹配，Agent 构建中 LLM 是大脑但循环和执行是代码的事。你现在更进一步：七道闸门把「要什么」和「怎么验证」变成硬门禁；AI 是运行时，流程、测试和 review 是代码。你在用 AI，但你不把判断权交给 AI。

7. **基础决定上限**。2026 年下半年先补分布式系统与网络协议栈，再补 C++、编译链接、GPU 和进程间通信。这些不是「手边的东西」，是**五年后依然成立的东西**。从「会用工具」往「能设计系统」走，又往「能写底层」走了一步。

8. **架构是规模的函数**。企业架构的「规模决定分工」和项目结构的「结构是发布单元的投影」是同一条思路：**没有普适最佳实践，只有与规模和边界匹配的方案。** 同一套模式，在小系统里是过度设计，在大系统里是必需品。

## 写作风格

- **中文 + 英文专业术语**。namespace、metaclass、decorator、reconciliation、Function Calling、fencing token 不做翻译——你知道这些词在中文里没有精确对应，强行翻译反而增加理解成本。

- **说 WHY 不说 WHAT**。你的文章从来不是 API 文档翻译——每一段都在解释「为什么这样设计」「不这样会有什么问题」。

- **生活比喻 + Mermaid 图，双管齐下**。比喻降低理解门槛，图理清结构关系。两者都已是 CLAUDE.md 正式约定，且**比喻已从语言类扩散到全站**。

- **Mermaid 有专属配色**（2026 年 7 月起）。深色底（`#1a1a2e` / `#16213e` / `#0f3460` / `#533483`）+ 品红描边 `#e94560`。图型分工明确：层次分类用 mindmap、流程用 flowchart、状态机用 stateDiagram、类关系用 classDiagram。**不看作者名，光看图能认出来。**

- **实战场景控制在 1-2 个**。你不会为了显得丰富而堆砌案例。一个完整的、有真实终端输出的例子，比十个伪代码片段有用。

- **系列内部的「钩链」结构**。System Design 每篇结尾有「与架构地图的衔接」mermaid 图，显式标注「本篇解决什么 → 留下什么问题 → 下一篇解决什么」。每篇文章同时是独立单元和链条一环。

- **三套稳定骨架**。理论/架构类：生活比喻 → 为什么需要 → 核心机制（编号小节）→ 实战代码 → 与下篇衔接 → 总结表格。源码阅读类：一句话概括 → Mermaid 架构图 → 关键代码摘录（标文件:行号）→「好在哪 / 用的什么模式 / 骨架代码」→ 小结 → 上下篇导航。跨语言/跨平台对照：设定同一个目标（下单/画三角形/项目结构），每个语言或平台独立成篇，最后用对照表收束。

- **总结表格化**。几乎所有新文章用 Markdown 表收尾（决策点、机制对比、配置清单、系列回顾），不是散的 bullet。

- **系列规模变大**。项目结构 9 篇、企业架构 20 篇、REA 15 篇。系列不再是 4-6 篇的小专题，而是能撑起一个子领域的完整结构。

- **证据链升级**（2026 年 10 月起）。C++/图形/项目结构示例实际编译运行；Metal/Vulkan 实跑，D3D11 交叉编译；Playwright 测试实际跑；文档检查实际跑 markdownlint/Redocly/链接检查，还做负向测试。**「看起来对」越来越不算数，「跑过」才算。**

- **源码阅读有固定结构**: clone 源码 → snake_case 笔记文件夹 → .gitignore + backup.sh 双排除。每个项目至少 8~10 篇，三层内容（架构学习 + 优秀代码 + Prompt 全集）。

## 你反复出现的模式

1. **从痛点出发**。每一篇文章的开头都是一段「你有没有遇到过这个问题」。写作结构是：痛点 → 原因 → 解决方案 → 为什么这样解决。

2. **对抗复杂性**。codebase-memory-mcp 是为了对抗 grep 全仓，RTK 是为了对抗 token 浪费，脱敏处理是为了对抗信息泄露——你的技术选择有一条清晰的主线：**让复杂的东西变简单，让隐性的东西变显性**。REA 用 131 行检查器守住 23 万行代码的依赖方向，Medusa 用 module link / query graph / workflow 代替跨模块耦合，T3 Code 只做控制面而不做新 Agent——都是同一个思路。

3. **薄封装优于厚抽象**。你对 QuantDinger MCP Server 的评价是「薄封装策略」，对 Colima 的喜爱是「只做一层薄薄的 VM 抽象」，对 LangChain 的态度是「先手写一个 Agent，再去看框架的源码」。你偏好那些让你离底层更近而不是更远的工具。free-stockdb 的五个薄入口共用一套 key 协议，QMT 在宿主进程里开一个服务窗口，EasyTHS 用外部 GUI 包装——都是薄封装。

4. **自托管优先**。GitLab 自托管、LOF 本地部署、QuantDinger 本地部署、Orbien 自建内网穿透——你宁可多花时间配置，也不愿意把数据和控制权交给云服务。T3 Code 的控制面、free-stockdb 的本地数据引擎，也是同一条思路。

5. **工程规范化**。脱敏处理约定、source-read 标准化流程、跨服务约定文档、语言版本约定、比喻写作约定、**用图解释约定**、**项目结构/文档/测试/Review 的规范**——你在用管理软件项目的方式管理知识库，而且**规范本身在持续长出新的条款**。

6. **规范先行，然后批量套用**。这是你 2026 年下半年最显著的工作方法：`source-read/README.md` 一天内迭代 4 次定好规范，然后 56 篇按新规范产出；企业架构先写总纲再批量展开 19 篇；项目结构先定「发布单元」再逐语言套用。先做工具，再做产品。

7. **提炼可复用的东西，而不是复述**。读源码不是写读书笔记——MetaGPT 那篇直接叫《7 段值得复制的 Python 代码》，deepseek-harness、Kun、ib_async 都以「关键代码模式精选」收尾。**你的产出物是「骨架代码」而不是「知识摘要」。** REA 的「约定 → 脚本 → 接线点」映射表、Medusa 的可回滚步骤执行器，都是能直接拿走的东西。

8. **对比作为论证结构**。你很难只讲一个东西——async/await 对比 Node.js/PHP/Go，设计模式每篇对比 GoF 原版语言，World Monitor 拉横表对比全部 4 个 Agent 框架，项目结构横跨 7 种语言，图形横跨 Metal/D3D11/Vulkan。**孤立地描述一个事物，说明还没看清它的边界。**

9. **可持续胜于一次性**。你对系统的偏好也体现在对自己的管理上——只是这件事在 2026 年下半年遇到了挑战：运动打卡和词汇学习都在 6 月下旬停下了，到 11 月仍未恢复。这本身是个值得留意的信号：**再好的系统也需要维护动作，而维护动作是最容易被挤掉的**。

10. **规模决定架构**。企业应用架构的 85 → 174 行、项目结构的「发布单元投影」、图形三平台的复杂度差异，都在说同一件事：**没有普适最佳实践，只有与规模和边界匹配的方案。** 你不再问「这个模式是不是最佳实践」，而是先问「这个系统有多大、边界在哪、谁来维护」。

11. **向下验证**。从 C++ 编译链接到 Metal/Vulkan 实跑，从 Playwright 测试到 markdownlint/Redocly 的实际输出——你越来越不接受「看起来对」。**能编译、能跑、能复现，才算结论。**
