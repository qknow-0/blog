# 跨服务约定：一套我自己维护的工程纪律

> 2026-06-10

这不是某个项目的 README，而是我在多个服务之间反复踩坑后固化下来的约定。每一条背后都有一段 debug 经历。

## 技术栈

- 所有服务统一使用 **Python 3.12 + uv** 管理依赖
  - `uv sync` 安装依赖
  - `uv run` 执行所有 Python 命令
- 测试框架统一使用 **pytest**（`uv run pytest`）

**为什么是 uv**：pip 的依赖解析慢、锁文件不稳定、虚拟环境管理需要手动操作。uv 把这几件事合到一个命令里，速度提升一个数量级。

## 部署与网络

- 顶层 `docker-compose.yml` 提供一键部署（基础设施 + 全部业务服务），使用内部网络
- `infra/` 目录提供独立开发环境，使用外部网络，用于本地按需启动单个组件
- 两套网络互相独立，互不冲突
- 容器间通过容器名互联（host 填 `postgresql` / `redis` / `kafka` 而非 `localhost`）
- 所有服务通过 `env_file: .env` 挂载统一环境变量

**为什么拆两套网络**：一键部署和按需开发是两个完全不同的场景。混在一起的结果是你改一行代码要重启半个集群，或者调试时搞不清流量从哪来。

## 数据库

共享同一个 **PostgreSQL** 实例，但各服务只碰自己的表和库。数据读取服务可以跨库查询，但写入各归各的。

**为什么不一个服务一个数据库实例**：开发阶段过度拆分数据库会引入不必要的运维复杂度。共享实例 + 独立数据库/表，在隔离性和简单性之间取了一个平衡。真到了需要独立扩展的时候再拆。

## 代码规范

- 模块和公共函数必须有 docstring，包含四要素：运行逻辑 + 输入 + 输出 + 示例
- 单个代码文件尽量控制在 **400 行**以内；如果改动后会超过 400 行，先询问是否需要拆分
- 中文沟通，专业术语（如 PostgreSQL、Redis、Kafka、iFinD、ORM）保留英文

**为什么是 400 行**：不是硬指标。但超过 400 行的文件几乎总是塞了多个职责。拆分的标准不是行数本身，而是「这个文件做几件事」。

## 文档与流程

- Push 前整体 Code Review，结果保存到 `code-review/YYYY-MM-DD.md`
- 完成的 plan 归档到 `docs/plans/YYYY-MM-DD-HHMM.md`
- 后续 TODO 写入 `docs/todos.md`，标记状态
- 推送前更新相关文档（README.md、CLAUDE.md）

**为什么 Code Review 要存档**：AI 辅助编程时代，每次改动的上下文比过去大得多。存档 review 结果，一是为了追溯（三个月后你知道为什么要这样改），二是为了 AI 在后续对话中有完整上下文。

## 日志

- 日志按天划分，优先使用按天滚动或按日期命名的日志文件

**为什么不接 ELK**：日志平台有价值，但在服务还没到需要分布式日志检索的阶段之前，按天滚动的文件是最简单、最可依赖的方案。不依赖外部服务，出问题看文件就行。

## 图形

- 使用 Mermaid 绘制，根据内容选择合适的图型：层次分类用 mindmap，流程/数据流用 flowchart

**为什么选 Mermaid**：纯文本、版本控制友好、不需要切工具。一张流程图改了之后，`git diff` 能显示改了什么——PNG 做不到。

## 安全

- `.env` 文件已被 gitignore，包含敏感凭证，禁止读取
- 禁止自动 push 或 commit，除非用户明确要求
- 禁止改动各个服务的代码，每个服务代码自己去修改
