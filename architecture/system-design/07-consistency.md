# Consistency：副本之间的数据账本

> System Design 架构地图系列第 7 篇。系列总览见 [index.md](index.md)。

## 生活比喻：两个人的记账本

你和合伙人各有一本账本（主库和从库）。你的账本记了一笔"客户付款 1000 元"，但合伙人的账本还没记上。此时合伙人查账——**他看到的钱和你看到的不一样**。这就是一致性问题。

一致性 = **多个副本/存储对同一份数据达成一致的保证程度**。

## 一致性不是一个开关，是一把刻度尺

"一致性"这个词在工程里被滥用了。实际是不同强度的保证：

## 强一致（Linearizability / 线性一致性）

**直觉定义：所有操作仿佛在某一时刻原子发生，任何读都看到"最后一次写完成后的值"。**

```text
时间轴 →
写 W(x=1)     [========完成========]
读 R(x)             → 必须返回 1（看不到 0）
```

| 实现方式 | 原理 |
|---------|------|
| 单机数据库 | 只有一个数据副本，天然线性一致 |
| 多数派读写 | Raft/Paxos，读也要过半数（quorum read） |
| ZooKeeper / etcd | 分布式协调就是为强一致而生 |

**代价：** 写入要等多数派确认，延迟高；任何副本不可用，写入就阻塞。**强一致 ≠ 高性能，而是高延迟换确定性。**

## 最终一致（Eventual Consistency）

**直觉定义：停止写入后，经过足够时间，所有副本最终会一致。** 至于中间多久、读到什么，都不保证。

```text
写 W(x=1) → 主库 ✅ → 从库还在同步（读者可能读到 0）
    ↓ 几百 ms 后
所有副本都 = 1 → 一致了
```

| 场景 | 能接受最终一致吗 |
|------|-----------------|
| 朋友圈点赞数 | ✅ 晚几秒无所谓 |
| 评论列表 | ✅ 自己评论马上消失不可接受！→ 需要"读己之写" |
| 订单状态 | ⚠️ 状态流转不能乱序 |
| 银行余额 / 库存 | ❌ 必须强一致或事务 |

**工程现实：90% 的数据可以用最终一致，关键是识别那 10% 不能用的。**

## 中间档：读己之写与会话一致性

最终一致最难受的场景是"我自己刚写的数据，刷新就没了"。缓解：

| 一致性级别 | 保证 | 实现 |
|-----------|------|------|
| Read Your Writes（读己之写） | 自己写的自己一定读得到 | 刚写完的请求强制读主库 |
| Monotonic Reads（单调读） | 不会读到"时光倒流" | 同一会话固定读同一副本 |
| Bounded Staleness（有界陈旧） | 最多落后 N 秒或 N 条 | 同步复制 / 半同步 |

## 一致性的经典指标：Quorum

多数派读写（Quorum）是实现可调一致性的数学工具。有 N 个副本，写要 W 个确认，读要 R 个副本一致：

```text
R + W > N   → 读和写的集合必有交集 → 读必能读到最新写入
```

```mermaid
flowchart TB
    subgraph N5["N=5 副本"]
        W3["写 W=3：等 3 个确认"]
        R3["读 R=3：对比 3 个副本取最新"]
    end

    W3 -->|"W+R > N：3+3>5 ✅"| R3

    style N5 fill:#1a1a2e,stroke:#e94560,color:#fff
    style W3 fill:#16213e,stroke:#e94560,color:#fff
    style R3 fill:#533483,stroke:#e94560,color:#fff
```

**这就是 DynamoDB/Cassandra 的调参依据**：想要强一致就 `W=N, R=1`（写等全部）或 `W=1, R=N`；想快就 `W=1, R=1`（读可能旧）。

## 解决冲突：当两个副本都写了

多主写入 / 网络分区时，同一个 key 可能被两个节点各自修改——版本冲突。

### 策略一：Last-Write-Wins（LWW）

谁的时间戳新听谁的。

- 简单，但**丢更新**——慢的时钟覆盖快的时钟
- 分布式场景时钟不可靠（NTP 漂移），用 Lamport 时钟/版本向量

### 策略二：版本向量 + 合并

```
用户 A 的购物车: [苹果, 香蕉]
用户 B 的购物车: [苹果, 橙子]
合并结果:        [苹果, 香蕉, 橙子]  ← 不是覆盖，是并集
```

CRDT（无冲突复制数据类型）就是为此设计——计数、集合、JSON 都有 CRDT 实现，多个副本并发修改后能自动合并出确定结果。

### 策略三：冲突交给业务

把冲突原样返回给用户/应用去仲裁。Git 就是这么做的——合并冲突时让你手动解决。

## 一致性对应用透明的层次

| 层级 | 谁保证一致性 |
|------|-------------|
| 单机数据库事务 | 数据库自己（ACID） |
| 分布式事务（跨库/跨服务） | 应用 + 协调器（2PC/Saga） |
| 消息队列 + 状态机 | 应用（幂等 + 重放） |
| 缓存与 DB | 应用（Cache-Aside） |

**越往下，保证一致性的责任越落到开发者身上。** 单体时代靠数据库 ACID 就行；微服务化后每个服务自己的数据库只能保证局部，全局一致性要靠业务代码设计。

## 实践检查清单

设计任何"多副本读写"功能时，问自己：

```
1. 这个数据能容忍读旧吗？容忍多久？
2. 用户自己刚写的数据，必须马上读到自己写的吗？
3. 两个并发写冲突时，覆盖可以吗？还是需要合并？
4. 写失败了一半副本，返回成功还是失败？
5. 网络分区恢复后，数据自动收敛吗？
```

答案组合决定你选哪档一致性。

## 与架构地图的衔接

Consistency 回答了"多副本之间怎么保证数据正确"，但所有方案都受制于一个根本定理——一致性和可用性不可兼得。第 8 篇 CAP 定理就是这个权衡的数学表述，也是理解分布式系统一切取舍的起点。

## 总结

| 强度 | 直觉 | 代价 | 典型实现 |
|------|------|------|---------|
| 强一致 | 读必见最新 | 写慢、可用性低 | 单机事务、Raft、etcd |
| 读己之写 | 自己写的读得到 | 路由逻辑 | 强制读主 |
| 有界陈旧 | 最多落后 N 秒 | 实现复杂 | 半同步复制 |
| 最终一致 | 终会一致 | 中间读到旧值 | 异步复制、DynamoDB |
| 冲突处理 | 覆盖 / 合并 / 人工 | 业务复杂度 | LWW、CRDT、Saga |
